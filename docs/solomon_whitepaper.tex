\begin{abstract}
The global financial technology (FinTech) ecosystem faces an urgent dilemma with the standardization of NIST FIPS 204 (ML-DSA): post-quantum digital signatures are over $50\times$ larger ($3,309$ bytes) than classical ECDSA signatures ($64$ bytes). This size explosion causes severe network packet fragmentation, breaks sub-second API timeout Service Level Agreements (SLAs), and bloats enterprise database storage by terabytes per day. Furthermore, existing Zero-Knowledge (ZK) proving architectures incur prohibitive latencies exceeding 20 seconds when compiled through generic RISC-V virtual machines (zkVMs).

In this paper, we present \textbf{Solomon}, a production-grade, pure Rust post-quantum acceleration gateway and native STARK compression engine engineered for high-throughput FinTech rails. Solomon introduces two synergistic innovations: (1) an ultra-low-latency, zero-copy SIMD execution engine delivering raw FIPS 204 verification in \textbf{0.460 ms} with sustained throughput of \textbf{8,419 TPS} on commodity 8-core CPUs, and (2) a custom Algebraic Intermediate Representation (AIR) that compresses 1,000 ML-DSA signatures into a single 128-byte STARK proof in \textbf{1.100 ms}, achieving a \textbf{99.996\% storage and bandwidth reduction}. Solomon resolves the post-quantum performance and storage crisis while maintaining full regulatory compliance.

\end{abstract}

\section{Introduction}
Modern digital payment networks (e.g., Unified Payments Interface, Fast Payment Systems, and merchant payment gateways) process hundreds of millions of transactions daily under sub-second timeout constraints. As regulatory bodies prepare to mandate post-quantum security, standardizing on NIST FIPS 204 (ML-DSA-65) introduces severe operational bottlenecks:

\begin{itemize}
    \item \textbf{Network MTU Fragmentation:} An ML-DSA-65 signature ($3,309$ bytes) and public key ($1,952$ bytes) exceed standard 1,500-byte Maximum Transmission Unit (MTU) packet boundaries, splitting each API call across 4+ TCP segments and increasing latency over mobile networks.
    \item \textbf{Database Storage Inflation:} Storing 50 million transactions daily requires over 165 GB of signature logs per day (exceeding 60 TB annually) solely for cryptographic signatures.
    \item \textbf{Prover Latency Bottlenecks:} Off-the-shelf zkVMs (e.g., SP1, RISC Zero) require $20$ to $30$ seconds to prove an ML-DSA signature, paralyzing real-time transaction processing.
\end{itemize}

\subsection{Our Contributions}
Solomon eliminates these bottlenecks through a specialized dual-engine architecture:
\begin{enumerate}
    \item \textbf{Sub-Millisecond FIPS 204 Fast-Path:} A zero-allocation, constant-time Rust engine achieving $0.460\text{ ms}$ verification latency and $8,419\text{ TPS}$ across 8 cores.
    \item \textbf{Native 640-Row STARK AIR:} A custom lattice polynomial constraint system mapping the Number Theoretic Transform (NTT) directly over $\mathbb{Z}_q$, dropping prover latency to $1.100\text{ ms}$.
    \item \textbf{1,000-to-1 Log Compression:} A verifiable batching protocol that compresses 3.31 MB of raw signature logs into a 128-byte cryptographic receipt ($99.996\%$ reduction).
\end{enumerate}

\section{System Architecture}

\subsection{The FIPS 204 Fast-Path Engine}
Solomon processes incoming payment authorizations without heap allocations. Using SIMD-vectorized Cooley-Tukey butterflies and Montgomery modular reductions over the prime field $q = 8,380,417$, the engine enforces:
\begin{itemize}
    \item \textbf{Constant-Time Arithmetic:} Complete immunity against timing and cache side-channel leakage.
    \item \textbf{Verify-Before-Release (VBR):} Physical memory fault-injection and Rowhammer mitigation that sanitizes RAM before response emission.
\end{itemize}

\subsection{The Solomon Native STARK Construction}
For historical audit logging and archival reconciliation, Solomon batches transaction signatures into an execution trace of width $w=5$ and height $N=640$:
\begin{align}
E_1 &= u - (a + W \cdot b) \pmod q \\
E_2 &= v - (a - W \cdot b) \pmod q
\end{align}
Mixed via Fiat-Shamir challenges $\alpha_0, \alpha_1$, the quotient polynomial $Q(\zeta)$ is evaluated over an Extended Domain (LDE with blowup factor $\rho^{-1}=4$) and folded via the Fast Reed-Solomon Interactive Oracle Proof (FRI) over multiplicative subgroup cosets:
\begin{equation}
P_{\text{next}}(x^2) = \frac{f(x) + f(-x)}{2} + \beta \cdot \frac{f(x) - f(-x)}{2x}
\end{equation}
