# Project Solomon: Tethered Proxy Architecture & Network Specification

## 1. Executive Summary & Architectural Philosophy
The Project Solomon network layer is designed as an **On-Premises Tethered Transparent Reverse Proxy**. 

To drive enterprise adoption, the system requires **Zero Code Changes** to legacy banking infrastructure. Instead of embedding cryptographic SDKs into monolithic legacy codebases, the Solomon Proxy intercepts HTTP/REST API traffic at the network edge, natively injects the ML-DSA-65 post-quantum signature into the payload, and forwards the secured transaction.

**The Prime Directive:** Unencrypted client data must never leave the host machine. Intellectual property (the Solomon ML-DSA engine) must never execute without live authorization from the Control Plane.

---

## 2. The Network Perimeter & Egress Security

The proxy must operate under strict, kernel-level network isolation. It assumes the host operating system is fundamentally hostile or vulnerable to lateral movement.

### 2.1 The Loopback Mandate
The proxy’s listening server (the Axum framework) must bind **exclusively to the local loopback interface (`127.0.0.1`)**. 
* **Rule:** It is strictly forbidden to bind the proxy to `0.0.0.0` or any public-facing IP address.
* **Why:** By binding to `127.0.0.1`, physical network interception is impossible. The legacy application server and the Solomon proxy communicate via local RAM memory streams, rendering external packet sniffing useless.

### 2.2 eBPF Egress Hardening
Upon deployment, the host environment must be configured with eBPF (Extended Berkeley Packet Filter) kernel rules restricting the proxy container's outbound network traffic to exactly two destinations:
1. `127.0.0.1` (Local legacy backend).
2. `api.solomon.in` (The Solomon Cloud Control Plane).
All other outbound packet requests must be instantly dropped at the kernel level to prevent data exfiltration in the event of a proxy compromise.

## 3. The Tethered Heartbeat (Anti-Piracy & Licensing)

To prevent container cloning, unauthorized execution, and intellectual property theft, the proxy relies on a Hardware-Attested Cryptographic Heartbeat.

### 3.1 Hardware Fingerprinting
Upon boot, the proxy must scan the physical host machine to generate a unique cryptographic hash combining:
* CPU architecture IDs.
* Primary network interface MAC addresses.
* Cloud provider instance metadata UUIDs (if running in AWS/Azure/GCP).

### 3.2 The Epoch Token Handshake
Every 24 hours, the proxy initiates a `reqwest` HTTPS payload to the Solomon Control Plane containing the `License_ID` and the `Hardware_Fingerprint`.
* If authorized, the Control Plane returns an `Epoch Token` containing the `Daily_Salt`.
* The `Epoch Token` is signed by the Solomon Master Ed25519 Private Key.
* **Verification Gate:** The local proxy must verify this signature against the hardcoded Solomon Public Key before unpacking the salt. 
* **The Mathematical Lock-In:** The proxy passes this `Daily_Salt` into the Phase 3 SHAKE-128 PRNG to initialize the ML-DSA grid matrix $\mathbf{A}$. Without this exact salt, the mathematical signatures generated by the proxy will fail global verification.

## 4. The Intercept & Sign Pipeline

When an incoming API request hits the proxy via `127.0.0.1:8080`, it must strictly follow this execution sequence:

1. **Payload Ingestion:** The Axum routing layer accepts the raw byte payload (`serde_json::Value` or raw bytes).
2. **Memory Pinning:** The payload and the bank's secret ML-DSA keys are loaded into specific, tracked memory registers.
3. **Execution Barrier:** The CPU is forced to execute an `LFENCE` (x86) or `ISB` (ARM) instruction to prevent speculative execution timing leaks.
4. **Signature Generation:** The proxy calls `crate::crypto::sign::ml_dsa_sign`, applying Arithmetic Masking (secret sharing) and execution shuffling to the NTT loops to defeat Deep Learning Side-Channel Attacks (DL-SCA).
5. **Verify-Before-Release:** The proxy internally calls `ml_dsa_verify` on its newly generated signature. If the signature is invalid (indicating a Rowhammer bit-flip fault attack), the thread instantly panics and aborts.
6. **Payload Forwarding:** The 2.4KB signature is injected into the HTTP Header (`X-Solomon-PQ-Sig`), and the payload is forwarded to the legacy destination.

## 5. Identity-Centric Zero-Knowledge (ZK) Authorization

To prevent network bandwidth bloat caused by the massive 2.4KB FIPS-204 signatures, the proxy implements Identity-Centric ZK Proofs.

Rather than executing the heavy polynomial matrix math inside a ZK-SNARK circuit (which causes unacceptable latency), the proxy shifts the proof mechanism:
* The Proxy executes the heavy ML-DSA math natively on the bare-metal CPU.
* Once verified, the Proxy generates a lightweight ZK-SNARK proof asserting: *"I am a mathematically authorized Solomon Proxy Node [Identity], running on un-tampered hardware [Attestation], and I have successfully validated the transaction signature [State]."*
* This compresses the authorization footprint to 128 bytes, allowing high-frequency trading and payment networks to operate without latency penalties.

## 6. Operational Security (OpSec) & Container Lifecycle

### 6.1 Zero-State Execution
The proxy must be entirely stateless and disk-silent. 
* **No Logging:** Unencrypted transaction payloads must never be written to stdout, stderr, or log files.
* **No Disk Caching:** Secret keys and daily salts must only exist in volatile RAM.
* **Memory Wiping:** Standard Rust `Drop` traits must be extended with `std::ptr::write_volatile` to explicitly overwrite memory arrays with zeros the exact microsecond a transaction goes out of scope.

### 6.2 Secure Enclave Deployment (Optional/High-Tier)
For Tier-1 financial institutions, the Rust proxy binary must be compiled against the `x86_64-fortanix-unknown-sgx` target.
* Running inside an **Intel SGX Secure Enclave** ensures memory encryption at the hardware level. 
* This physically prevents the bank's own system administrators from dumping the RAM to extract the ML-DSA private keys, creating absolute Zero-Trust cryptographic isolation.

### 6.3 Crash-Only Fault Tolerance
If the proxy detects a hardware anomaly, an invalid signature output, an unauthorized epoch token, or a failed strict-monotonicity hint check (CVE-2026-24850), the container must follow a **Crash-Only** architecture. It must not attempt to recover or fail open. It must instantly wipe memory and terminate the process with exit code `1`.
