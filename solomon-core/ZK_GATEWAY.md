# Project Solomon: Zero-Knowledge Gateway Specification

## 1. Executive Summary & Mission
The Zero-Knowledge (ZK) Gateway is the ultimate technical moat for Project Solomon. 

While the Tethered Proxy successfully intercepts and secures transactions using NIST FIPS 204 (ML-DSA-65), the resulting signatures are approximately 2.4KB. Sending this massive cryptographic footprint to legacy banking mainframes causes unacceptable network bloat and database strain. 

The ZK Gateway solves this by shifting the architecture to **Identity-Centric Zero-Knowledge Authorization**. Using the SP1 zkVM, we verify the heavy ML-DSA-65 signature locally and compress that verification into a mathematically undeniable, 128-byte SNARK proof.

**Primary Objectives:**
1. Eliminate network bandwidth bloat for legacy enterprise clients.
2. Cryptographically decouple the transaction payload from the raw Post-Quantum signature.
3. Establish a standard SP1 Host/Guest proving architecture.

---

## 2. Technical Stack & Workspace Architecture
This component is completely isolated from the local proxy to prevent dependency conflicts between standard Rust execution and RISC-V compilation.

* **Language:** Rust
* **zkVM Framework:** Succinct Labs SP1 (`sp1-sdk` and `sp1-zkvm`)
* **Target Architecture:** `riscv32im-succinct-zkvm-elf`

### Workspace Topology
The repository utilizes a strict split-workspace design:
* `/guest`: The program compiled to RISC-V that executes *inside* the ZK circuit.
* `/host`: The standard executable that manages the inputs, generates the proof, and acts as the bridge to the Solomon Proxy.

---

## 3. The Guest Circuit (`/guest`)

The guest program represents the undeniable mathematical truth. It does not generate signatures; it strictly verifies them.

### 3.1 Input State
The circuit must read the following parameters from the zkVM environment:
1. `public_key`: The bank's master ML-DSA-65 public key.
2. `transaction_payload`: The raw byte array of the transaction (e.g., `{"amount": 5000}`).
3. `signature`: The 2.4KB ML-DSA-65 signature generated by the Solomon Proxy.

### 3.2 Execution Logic
1. **Verification Gate:** The circuit executes a pure-Rust implementation of the `ml_dsa_verify` function using the provided inputs.
2. **Failure Condition:** If the signature is invalid, the circuit must immediately `panic!`. A panicking circuit cannot produce a valid proof.
3. **Public Commitment:** If the signature is mathematically valid, the circuit hashes the `transaction_payload` (e.g., using SHA-256) and commits this hash to the SP1 public journal using `sp1_zkvm::io::commit()`.

*Security Note:* The raw signature and public key remain private inputs. They are *not* committed to the journal, ensuring absolute zero-knowledge compression.

---

## 4. The Host Prover (`/host`)

The Host program acts as the high-performance orchestration layer. In production, this will run on the same physical hardware as the Solomon Proxy, utilizing GPU acceleration (CUDA) if available.

### 4.1 Execution Flow
1. **ELF Ingestion:** The Host loads the pre-compiled RISC-V ELF binary of the Guest program.
2. **Stdin Preparation:** The Host receives the raw transaction, public key, and signature from the local Solomon Proxy. It writes these into the `SP1Stdin` buffer.
3. **Proof Generation:** The Host invokes the `ProverClient` and executes the ELF binary against the Stdin buffer to generate a succinct `SP1ProofWithPublicValues`.
4. **Verification & Delivery:** The Host verifies the generated proof locally to ensure integrity, extracts the committed transaction hash from the public values, and returns the 128-byte SNARK proof to the Solomon Proxy.

---

## 5. Network Lifecycle Integration

Once this ZK Gateway is integrated with the main Solomon Tethered Proxy, the full lifecycle of a transaction becomes:

1. **Intercept:** Proxy catches `{"amount": 5000}`.
2. **Sign:** Proxy generates the 2.4KB ML-DSA-65 signature.
3. **Prove:** Proxy sends payload and signature to the local ZK Gateway. The ZK Gateway verifies it and generates the 128-byte SNARK proof.
4. **Forward:** Proxy attaches the *SNARK Proof* (not the ML-DSA signature) to the payload and forwards it to the bank's backend.
5. **Settle:** The bank backend verifies the SNARK proof in microseconds.

---

## 6. Operational Constraints
* **Cycle Count Limits:** ML-DSA-65 verification is computationally heavy. The SP1 guest must be heavily optimized to keep the cycle count within feasible proving limits.
* **Deterministic Execution:** The Guest program must be strictly `#![no_std]` and absolutely deterministic. It cannot access system time, network sockets, or hardware RNGs.
